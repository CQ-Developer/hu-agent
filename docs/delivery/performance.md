# 性能验证报告（v1 交付）

> 结论摘要：在**单机自测**环境下（API + PostgreSQL + Redis + MinIO + 压测客户端同机），
> 4 个核心写/读路径均无一失败，读路径 305 rps、用量上报 39.7 批/秒（≈2,000 事件/秒）、
> 快照上传 28 MiB/s、登录 18 rps（argon2id 故意设计为 CPU 昂贵）。
> **这是下限基线，不是容量证书**：生产容量需在 staging 以目标拓扑复测（见第 5 节）。

## 1. 方法

- 工具：`scripts/benchmark.py`（标准库实现，请求形状与真实客户端一致：`app/src/main/sync/backend.ts`、`cloud/client.ts`）
- 场景与负载：

| 场景 | 单次操作 | 说明 |
| --- | --- | --- |
| `login` | 登录一次 | argon2id 校验 + 设备/会话写入；**服务端 CPU 最重路径** |
| `usage:batch` | 上报 50 条事件 | 校验 + 幂等判定 + 分区写入；客户端默认上报形态 |
| `stats` | `GET /stats/usage?scope=self&groupBy=day` | 库侧聚合读 |
| `snapshot` | init → 预签名直传 1 MiB → complete | 端到端上传（含 sha256 流式校验）；每线程独占一个工作空间避免乐观锁冲突 |

- 并发档位：1 / 4 / 8；每档 24 次操作（共 288 次操作，0 失败）
- 复现：`uv run --project management python scripts/benchmark.py --scenario login,usage,stats,snapshot --concurrency 1,4,8 --iterations 24`

## 3. 结论与容量推算

| 路径 | 观测上限（单机） | 推算与余量 |
| --- | --- | --- |
| 用量上报 | 39.7 批/秒 ≈ **1,985 事件/秒** | 5,000 客户端每 5 分钟上报一次 ≈ 17 事件/秒 → **用量约 0.9%** 的实测上限；上报是异步重试队列，可容忍抖动 |
| 统计读 | **305 rps**（P95 45 ms） | 管理台/客户端零散查询，余量充足；C8 仍未饱和（C1→C8 单调上升） |
| 快照上传 | **28 MiB/s**（P95 380 ms @C8） | C4 起饱和，瓶颈是同机磁盘/回环；客户端直传对象存储（不经 API），多客户端并行时吞吐随对象存储扩展 |
| 登录 | **18 rps**（P95 695 ms @C8） | 1,000 人同时登录需 ~55 秒（一次性事件）；argon2id 成本是安全设计，不建议调低 |

**延迟预期（供上线后对基线）**：读 P95 < 100 ms、写 P95 < 400 ms、登录 P95 < 700 ms（本机环境）。

## 4. 压测中发现的问题

| # | 发现 | 处置 |
| --- | --- | --- |
| 1 | **快照被写入技能包桶**：`get_object_store()` 恒用 `s3_bucket_skills`，`s3_bucket_snapshots` 从未生效（分桶生命周期/权限策略无法生效） | 已修复：按用途分桶的 `get_object_store("snapshots")`；新增 `tests/test_object_store.py`（分桶隔离/实例复用/非法用途）与 stage6 集成断言 |
| 2 | **办公室 NAT 下的登录限流风险**：默认 `login_ip_limit = 10/分钟/IP`，同一出口 IP 的整间办公室 1 分钟只能登录 10 次 | 已记入 `docs/delivery/deployment.md`（部署建议上限/按账号维度限流）；客户端登录失败提示保留 |
| 3 | 观测项：`POST /workspaces/{id}/snapshots:init` 返回 200（其他创建类接口为 201） | 仅记录，客户端按 2xx 判定；如需统一可在 v1.x 收敛（需同步客户端与 openapi） |

## 5. 局限与必须重做的验证（不隐瞒）

1. **所有组件同机**：API、数据库、缓存、对象存储与压测进程共享 CPU/磁盘/回环，数值偏乐观于"隔离部署"、
   偏悲观于"多副本水平扩展"，不能外推为生产容量；
2. **单 API 进程**：uvicorn 默认单 worker，未测多 worker/多副本；
3. **无 TLS/代理**：未包含 TLS 握手、反向代理与 WAF 开销（管理台/客户端生产必须走 HTTPS）；
4. **并发规模小**：最高并发 8，未逼近队列饱和点，因此"上限"栏应理解为**已测吞吐**而非拐点；
5. **数据规模小**：`usage_events`/快照表为开发规模（万级），分区裁剪与索引在百万级下的表现未验证。

**staging 复测清单**（发布前完成）：按目标拓扑（多副本 API + 独立 PG/S3 + TLS 反代）复跑本脚本，
并发上探至 64/128，数据量灌入 ≥ 100 万事件与 ≥ 100 个快照，记录拐点与错误率；结果回填本文档。
